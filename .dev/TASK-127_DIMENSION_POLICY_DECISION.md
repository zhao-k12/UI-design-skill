# TASK-127 — ARCHITECTURE_CONFLICT: fixed-size admission

Current design: V0.2.8 `contentScope.width/height` are copied from one native snapshot and treated as an exact admission condition by Registry, Core assembly, the list layout gate and Figma Adapter. The headed Table's original Figma master also has fixed-width row and cell children. Resizing only its outer instance to 1660 px leaves 1841 px rows overflowing.

Cause and impact: the source sample dimensions were conflated with content/style identity. Every new list content width can trigger an unnecessary component rebuild, repeated FAIL and long Figma work. Simply deleting the checks would permit visually broken output.

User decision (2026-10-22): remove all fixed-size admission conditions. Implement in a new version so historical locked tasks remain reproducible. Content, official source, typography and non-dimensional visual rules remain gated. A component's measured sample size is evidence, not its allowed size. Layout policy chooses intrinsic size or fill width; only a native master proven to respond to width changes can use fill width. The new headed Table master `299:3` was built from the admitted source-linked master and its 1660 px instance `299:36` retains a real main-component link with full-width rows, three equal columns and full-width borders. Other components remain intrinsic until their own resizing behavior is verified; they no longer fail admission merely because a surrounding Cell has a different width.

Proposed dependency changes: versioned Registry content scopes without width/height or per-column pixel widths; separate sizing policy; Core places fill-width instances in their Cell while leaving intrinsic controls at source-measured size; Figma Adapter accepts a source-bound positive size under that policy; layout and readiness gates check overflow/content instead of equality with a historical snapshot. The native page, independent readback and final visual QA remain blocking.
