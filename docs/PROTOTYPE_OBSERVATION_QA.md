# 原型观察与内容验收

这份记录用于把截图中的“实际可见”与最终页面的“应当保留”分开。它是当前原型的审核材料，不是固定页面模板，也不提供视觉尺寸。开始布局前完成一次逐区观察；后续各阶段复用同一来源编号，避免反复重新读图。

## 来源观察清单

记录原型文件及其 SHA-256，并按区域为**每个可见控件或重复实例**分配稳定编号和位置说明。除了文字、字段、表格列与可见数据，还要记录图标、头像、徽标数字、输入框前后缀、菜单箭头、按钮内图文顺序，以及几个元素是否属于同一个控件。把图标—文字、头像—文字、树符—名称、按钮—容器分隔线等相邻关系单独编号；共性关系可用一条规则覆盖多个实例，例外单列。对可见的呈现类别至少区分无底／填充／描边、圆点／图标、圆形／胶囊／矩形；这是选官方变体的依据，不是抄取截图的像素或精确色值。无法辨认图标时记录可见形态及用途；影响业务识别或用户明确要求准确还原的内容保留 Review，非关键装饰可按入口规则合理替代并记录取舍，不冒称原始素材。

重复结构先提炼共性，再逐项点数并核对例外：每个一级菜单分别记录有无展开箭头；表格每个可见状态分别记录背景类别、状态点和文字；每行操作分别记录图标与文案。不可用“菜单均有图标”“表格使用状态标签”等总括句代替逐项检查。

每条观察只作一种决定：

| 决定 | 所需记录 | 后续检查 |
| --- | --- | --- |
| 纳入 | Tree 来源项及文字或非文字属性、控件关系 | 骨架标注，默认组件结构，最终可见结果逐项对应 |
| 排除 | 原型中的位置和可核对的理由，例如工具悬浮层或被划除的旧稿 | 最终页面不得悄悄带入；审核中可追溯 |
| Review | 不确定点、可能的两种解释及其对页面的影响 | 影响功能或主要内容时，在骨架前请用户确认；未解决不得把相关内容记为 PASS |

疑似遗留元素不能仅凭“不好看”“不符合 iView 风格”排除。结合区域归属、同类控件的一致性、业务关系及原型工具边界判断；证据不足时保留 Review。保留原始观察，不用归一化 Tree 改写截图事实。排除或 Review 的判断只影响本次原型，不继承到下一张图。

## 原图独立复扫与变体选择

### 非关键替代证据

来源单项保留原图 `traits`。确认为非关键、没有业务识别影响且用户未要求精确还原，并已决定合理替代时，在来源项填写 `substitution: {status: "resolved", importance: "noncritical", businessCritical: false, exactRequired: false, description: "实际替代内容", reason: "非关键的具体依据"}`，`sourceEvidence` 仍描述原图和替代的区别，绑定实际节点。不要从截图自动推断关键性；用户指定素材或明确要求优先。

`delta-v1` 复核时在 `substitutions` 中以来源项 id 为键，单独填写 `renderedTraits`（实际截图中的 leading/trailing/surface/shape/role）、与来源一致的 `description`、非关键 `reason` 和实际目视结果 `renderedEvidence`。两者不同时由审核记录明确差异，不能复制原图特征作为实际截图特征；缺少真实复核或关键性不明时不提交通过。该机制只能检查记录完整和一致，不能证明人工判断或截图事实。替代项使用单项来源记录；普通批量复核的共性组不能代替替代项的独立证据。

完成第一份观察和 Tree 后，暂时不看这两份材料，只看原图，按顶栏、侧栏、主内容、浮层、表格列与每个可见行重新列一份观察。再核对两份清单的编号、数量及可见特征；差异返回原图解决，不能直接让第二份抄第一份。这样才能发现“清单里根本没记录的箭头”，而不是只证明已经记录的项都进入了页面。

为每个纳入项记录候选官方组件、变体/API 和选用理由。先同时核对角色、前后图标、背景类别、边框、形状与状态，再选变体。例如带圆点且有填充背景的状态标签，不能仅因有圆点就选运行后呈白底描边的变体。官方运行结果与原型的呈现类别不相符时，返回组件选择；若官方无合适变体，记录规范缺口并按流程处理，不用自定义 CSS 伪造。原型的精确颜色、尺寸、间距和字体仍不进入官方样式依据。

## 一次综合核对，四类结论

1. **Tree**：原图独立复扫与初稿清单逐项一致后，每条观察都有决定；纳入项的文字、呈现类别和控件关系均映射到 Tree，排除项有理由，影响业务或用户明确要求的未解决 Review 阻断相关区域；非关键图形按入口规则记录合理替代后完成复核。只校对文字不足以通过。
2. **骨架**：纳入项对应区域和组件选型；每个菜单项的展开提示、图标槽位、头像、徽标、下拉及状态标签形态须有可见标注。在同一结论内核对整页重点、区域比例、密度、主题可读性及官方组合依据，而非只看组件位置和无越界；结合[项目默认主题与表单](IVIEW_COMPOSITION_PATTERNS.md#项目默认主题与表单)核对有侧栏时通常采用浅色顶栏、常规表单标签左右排列，例外有适用理由。表单项排列和内部标签方向分别判断；不增加审核轮次。
3. **默认组件**：通过官方组件 DOM、API 与截图验证控件类型、变体和附属结构，尤其检查 Input 的前后缀、Badge、Avatar、Dropdown、Menu/Submenu、Tag/Badge 等。文案暂用默认内容，不因未填原型文字而漏掉结构；不能用“组件存在”代替“变体正确”。
4. **交付**：从原图逐区逐项对照最终整页截图，核对文字、数据、每项菜单箭头、每行状态填充／圆点、操作图标、头像、徽标、控件类型及图文相对位置；对排除项复核理由。记录未覆盖、不可见或不一致项并返回最早受影响阶段修复。

### 设计参考落地与核对

本节是可选的组合决策，不是固定页面模板。当前原型和本次明确要求决定业务内容及状态；用户提供的设计稿用于视觉和布局参考，通用规则在缺少明确依据时作为默认。明确给出的原型分页总数、当前页和每页数量优先于演示默认值；总数未知才使用已约定的演示配置，不能将参考稿示例总数说成真实数据。保留原型记录之间的差异和真实空值，不复制参考稿的业务数据或品牌内容。

- **框架**：判断Logo、顶部工具区、侧栏和主区的归属及边界。有侧栏且Logo位于其顶部时，Logo区域与侧栏共宽并与顶部工具区垂直协调；Logo属于顶栏时同样与侧栏宽度对应。侧栏背景贯穿可见高度，检查内容滚动时的连续性。Logo 始终使用默认素材，只有用户明确要求其他 Logo 或文字替代时才覆盖，不从原型或参考稿推断替换授权。
- **导航和工具**：根据实际层级配置一级、二级菜单、缩进、展开与选中状态。侧栏折叠、消息等顶栏工具按原型或本次设计要求决定，参考稿有某工具不意味着所有页面都应增加；头像与名称保持紧凑分组，末端留出空间。
- **查询区**：普通桌面表单默认标签在左、控件在右，同组标签和控件对齐；根据字段内容选择协调的控件宽度。查询、重置及适用的展开操作归属表单并依次排列，按四列布局在空余列或下一行右对齐；图标按选定风格及实际需要配置。
- **列表组合**：筛选区和表格区可分别组织，状态Tabs、数量徽标、工具栏和分隔线按当前页面及参考风格组合。需要时用独立徽标表示数量并让分隔线覆盖相应内容区；不把参考页面的Tabs、标题或工具强加到其他页面。
- **表格**：按列语义配置宽度与对齐：文字、数值、日期和操作分别判断；检查表头字重、行高、底色、分隔线及工具栏与表头间距。参考风格要求条纹时优先使用已核实的官方表格能力，长文本和操作列须避免挤压。操作的图标与颜色可按项目风格配置，危险操作的表现不从单一参考推成全局规则；主动配置的图标使用Remix Icon。
- **分页**：右下对齐，按本次明确的原型配置和既有默认策略选择总数、页码、每页条数与跳转；参考稿展示跳转并不自动覆盖现有默认。记录演示数据与真实数据的区别，确保总数、页数及每页条数相互一致。

在已有整页审查中同时检查上述适用项与当前原型的内容，先汇总所有已发现问题，再批量修正并复核相关区域及全局关系。选择条纹、徽标、对齐或分页属性前核实锁定版本的官方API与适配器是否支持；不为追求参考效果伪造官方样式。若无法实现，记录具体限制及实际结果，不把未实现的视觉差异写成通过。整合到已有Tree和review，不新增单独报告或检查阶段。

### 页面质量核对

在原有同一次整页复核中按实际适用区域核对，不新增审查轮次，也不将某一截图布局变成通用模板：

- **页面壳与导航**：品牌、顶栏、侧栏和主区的归属、连续背景、边界及选中项是否符合本次原型和已选主题；头像与名称、图标和文字保持合理分组和间距。
- **筛选与操作**：选中项是填充、描边还是文字强调，输入框的前后缀、筛选状态和动作次序是否正确；不凭名称判断组件变体或补造未展示的业务选项。
- **表格与数据**：核对列顺序、每行文字与空值、状态及对应操作；状态点、背景类别与形状、操作的颜色和图标均应在当前截图中核实；工具栏、表头、单元格和分页之间保持可读且无挤压。
- **整体节奏**：检查信息主次、字体层级、区域比例、疏密和对齐；原型展示内容保留，允许按已核实官方组合调整偶然空白，不要求像素级复制。

来源特征须逐区域反映原图实际表现，例如有图标的菜单不能全部写成`leading:none`，带浅色填充和圆点的状态不能统称无底普通文本；共同特征可分组，状态差异和例外仍需保留。独立复扫必须再次看原图记录，禁止程序直接复制初读或由Tree反推复扫。最终检查时逐项比较原型和本轮截图：如有业务错误、错误选中状态、缺失内容、遮挡或重要视觉类别不符，记录在现有差异中并修正；再次检查受影响项及全局关系。若所选官方组件无法表达所需外观，先核实其他官方变体或插槽及现有适配能力，必要时记录来源或适配限制；不能将不一致写成一致或仅凭自动检查PASS发布。非关键标记和小图标按入口的合理替代规则处理。

`delta-v1`的确认只表示审阅者确认相应内容，展开器会依据预期生成部分审核字段，不能独立证明截图与原图一致；`review-plan.json`和自动结构检查不识别所有视觉差异。视觉未核实、来源特征写错或有未解决的重要差异时，不得将相应组确认或将问题清空以通过发布。对已确认的非关键替代如实记录原图特征、实际特征和理由。

QA 保存原型哈希、两次独立观察、每项编号及决定、Tree 绑定、官方变体理由和三张内部／最终截图哈希。Tree、骨架、组件、交付四类结论在**同一次综合审查**中记录；每项不再重复写四次 PASS。自动检查核实结构、DOM 和编号覆盖；原图到最终静态截图的独立目视校对判断角色、相邻关系与变体。不可把文字齐全、组件数量或页面可渲染写成完整 PASS。

整页布局关系同样必须覆盖：侧栏背景是否连续、区域边界是否符合本次归属、标题/工具栏是否按选定组合对齐且不跨分隔线。区分顶对齐、基线和居中，不再要求所有Card工具栏中心相等。使用[布局关系检查](HTML_FAST_WORKFLOW.md#布局关系检查)的实际测量，在原有review中确认`checkedLayoutRelations`；其余视觉关系仍在同一审查中核对。不能用“使用官方组件”或机器无越界代替整页效果证据，不复用未覆盖这些内容的历史PASS。

## 列表条数、空值与裁切

这是用户批准的静态展示默认政策，不是iView官方规定。普通业务记录列表默认交付10条完整记录，右下角放官方默认Page分页器；用户针对本次页面明确指定数量/分页方式或原型给出明确分页配置时优先遵循。分类矩阵、有限业务时段、时序采样、详情子表等不自动按普通记录补裁；汇总行独立保留，不计入普通记录数。按实际语义判断，不增造分类或采样点。

| 来源情况 | 交付处理 |
| --- | --- |
| 完整记录超过10条 | 只取前10条；其余记录不保存在交付Tree数据或HTML中。初读/复扫仍记录实际可见数量，对不纳入记录注明用户展示政策，不谎称未看见。 |
| 完整记录不足10条 | 保留已有记录，补充演示记录至10条。模型逐条明确完整字段、值、状态和对应操作，保存完整数据；工具不按数量自行扩写。补充遵循已有字段格式和业务关系，不把所有空字段填满。 |
| 整条记录仅露出裁切片段 | 记录片段及裁切事实，不直接创建只有日期等内容的残缺交付行；缺少的展示行按演示补充政策生成，不能把推定值说成已识别原文。 |
| 完整记录中备注等单元格清楚可见但为空 | 保留空值，不因其它行有值而补写；原型明确的“无”或“—”保留其表达。 |
| 单元格被遮挡/裁切而内容未知 | 与空值区别记录。能明确业务结构时可作为演示补充并标注，关键业务含义仍不明则按现有Review处理，不猜称真实内容。 |

在现有观察项/组的`sourceEvidence`及排除`reason`中记录：原图完整条数、裁切片段、保留的来源行号、补充的演示行号及依据、截去范围；不另建报告或输入语言。独立复扫只记实际可见内容，不能把补充记录放进scan假称原图事实。完整Tree保存最终实际10行数据，现有视觉复核分别核对来源行未被改写、补充行被内部标明、空值保留、最终条数与分页位置。来源哈希绑定原图，不作为演示数据真实来源的证明。

分页器用锁定包的官方Page及默认样式，通过布局容器右对齐；默认第1页、每页10条、10页，展示“10条/页”选择，默认不增加总数文案或跳转。原型未提供真实总数时配置演示总数100，只作为用户指定的静态展示示意，内部标明非真实数据；原型或用户明确给出总数/分页配置时优先保留。分页存在不意味着实现翻页、hover或接口。

锁定包的`Page`默认可用属性为`modelValue: 1`、`pageSize: 10`、`total: 100`、`showSizer: true`；其余采用官方默认。以上100为演示总数配置，并非真实业务数据；本地Adapter如不能传递这些属性应按适配缺口处理。

## 新任务的结构化复核门

常规任务采用[快速入口](HTML_FAST_WORKFLOW.md)的紧凑分组输入；逐项编号和以下完整文件由程序展开，AI不重复手写。独立复扫只简记自己从原图看到的组数量、特征、数据差异和例外，仍须实际重看原图，不能从初读自动生成确认。最终复核共同规则只写一次且明确实际检查证据；展开器不会自动判视觉PASS。下面是展开后的证据契约，亦兼容历史输入。

为本次原型保存 `source-observations.json`、`independent-scan.json` 和 `visual-review.json`，三者都绑定原图 `sourceSha256`。前两份分别来自初读和不看初稿的原图复扫；每个可见实例有同一稳定 `id`、`region`，以及 `traits` 中的 `leading`、`trailing`、`surface`、`shape`、`role` 五项呈现类别。初读还记录 `sourceEvidence`、`decision`，纳入项有 `treeRef`，排除项有 `reason`。即使多个菜单共用规则，也要逐项编号。复扫材料只记从图上看到的内容，不复制初读结论。

新任务采用 `reviewMode: "batched-v2"`：顶层 `variantRules` 为每类官方变体只记录一次 `id`、`component`、`variantReason`、`officialEvidence`（锁定版官方源码／文档路径）；每个纳入项只填 `variantRef` 和五项 `renderedTraits`，排除项填 `exclusionStatus`。顶层 `stageChecks` 对 Tree、骨架、组件、交付各给一次结论。初读的顶层 `relations` 每条含稳定 `id`、被覆盖实例的 `sourceIds`、`kind`、`sourceEvidence`；独立复扫的 `relations` 复核相同编号、实例、关系类别并写 `visual` 所见；最终 `relationChecks` 为每个关系记录 `status`、`officialEvidence`、`renderedEvidence`。例如图标与文字的共同间距只写一条关系及其覆盖的实例，例外另列。文件还须锁定三张截图 SHA-256。工具核对来源、实例、关系、综合结论和截图字节；旧任务逐项 `checks` 格式仍可读取，但新任务不用重复填写。

