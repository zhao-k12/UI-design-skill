# 原型观察与内容验收

这份记录用于把截图中的“实际可见”与最终页面的“应当保留”分开。它是当前原型的审核材料，不是固定页面模板，也不提供视觉尺寸。开始布局前完成一次逐区观察；后续各阶段复用同一来源编号，避免反复重新读图。

## 来源观察清单

记录原型文件及其 SHA-256，并按区域为**每个可见控件或重复实例**分配稳定编号和位置说明。除了文字、字段、表格列与可见数据，还要记录图标、头像、徽标数字、输入框前后缀、菜单箭头、按钮内图文顺序，以及几个元素是否属于同一个控件。把图标—文字、头像—文字、树符—名称、按钮—容器分隔线等相邻关系单独编号；共性关系可用一条规则覆盖多个实例，例外单列。对可见的呈现类别至少区分无底／填充／描边、圆点／图标、圆形／胶囊／矩形；这是选官方变体的依据，不是抄取截图的像素或精确色值。无法辨认具体图标时记录其可见形态和用途为 Review，不猜测图标名称或资产。

重复结构先提炼共性，再逐项点数并核对例外：每个一级菜单分别记录有无展开箭头；表格每个可见状态分别记录背景类别、状态点和文字；每行操作分别记录图标与文案。不可用“菜单均有图标”“表格使用状态标签”等总括句代替逐项检查。

每条观察只作一种决定：

| 决定 | 所需记录 | 后续检查 |
| --- | --- | --- |
| 纳入 | Tree 来源项及文字或非文字属性、控件关系 | 骨架标注，默认组件结构，最终可见结果逐项对应 |
| 排除 | 原型中的位置和可核对的理由，例如工具悬浮层或被划除的旧稿 | 最终页面不得悄悄带入；审核中可追溯 |
| Review | 不确定点、可能的两种解释及其对页面的影响 | 影响功能或主要内容时，在骨架前请用户确认；未解决不得把相关内容记为 PASS |

疑似遗留元素不能仅凭“不好看”“不符合 iView 风格”排除。结合区域归属、同类控件的一致性、业务关系及原型工具边界判断；证据不足时保留 Review。保留原始观察，不用归一化 Tree 改写截图事实。排除或 Review 的判断只影响本次原型，不继承到下一张图。

## 原图独立复扫与变体选择

完成第一份观察和 Tree 后，暂时不看这两份材料，只看原图，按顶栏、侧栏、主内容、浮层、表格列与每个可见行重新列一份观察。再核对两份清单的编号、数量及可见特征；差异返回原图解决，不能直接让第二份抄第一份。这样才能发现“清单里根本没记录的箭头”，而不是只证明已经记录的项都进入了页面。

为每个纳入项记录候选官方组件、变体/API 和选用理由。先同时核对角色、前后图标、背景类别、边框、形状与状态，再选变体。例如带圆点且有填充背景的状态标签，不能仅因有圆点就选运行后呈白底描边的变体。官方运行结果与原型的呈现类别不相符时，返回组件选择；若官方无合适变体，记录规范缺口并按流程处理，不用自定义 CSS 伪造。原型的精确颜色、尺寸、间距和字体仍不进入官方样式依据。

## 一次综合核对，四类结论

1. **Tree**：原图独立复扫与初稿清单逐项一致后，每条观察都有决定；纳入项的文字、呈现类别和控件关系均映射到 Tree，排除项有理由，Review 对应的问题已解决或阻断相关区域。只校对文字不足以通过。
2. **骨架**：纳入项对应区域和组件选型；每个菜单项的展开提示、图标槽位、头像、徽标、下拉及状态标签形态须有可见标注。在同一结论内核对整页重点、区域比例、密度、主题可读性及官方组合依据，而非只看组件位置和无越界；结合[项目默认主题与表单](IVIEW_COMPOSITION_PATTERNS.md#项目默认主题与表单)核对有侧栏时通常采用浅色顶栏、常规表单标签左右排列，例外有适用理由。表单项排列和内部标签方向分别判断；不增加审核轮次。
3. **默认组件**：通过官方组件 DOM、API 与截图验证控件类型、变体和附属结构，尤其检查 Input 的前后缀、Badge、Avatar、Dropdown、Menu/Submenu、Tag/Badge 等。文案暂用默认内容，不因未填原型文字而漏掉结构；不能用“组件存在”代替“变体正确”。
4. **交付**：从原图逐区逐项对照最终整页截图，核对文字、数据、每项菜单箭头、每行状态填充／圆点、操作图标、头像、徽标、控件类型及图文相对位置；对排除项复核理由。记录未覆盖、不可见或不一致项并返回最早受影响阶段修复。

QA 保存原型哈希、两次独立观察、每项编号及决定、Tree 绑定、官方变体理由和三张内部／最终截图哈希。Tree、骨架、组件、交付四类结论在**同一次综合审查**中记录；每项不再重复写四次 PASS。自动检查核实结构、DOM 和编号覆盖；原图到最终静态截图的独立目视校对判断角色、相邻关系与变体。不可把文字齐全、组件数量或页面可渲染写成完整 PASS。

整页布局关系同样必须覆盖：侧栏背景是否连续、区域边界是否符合本次归属、标题/工具栏是否按选定组合对齐且不跨分隔线。区分顶对齐、基线和居中，不再要求所有Card工具栏中心相等。使用[布局关系检查](HTML_FAST_WORKFLOW.md#布局关系检查)的实际测量，在原有review中确认`checkedLayoutRelations`；其余视觉关系仍在同一审查中核对。不能用“使用官方组件”或机器无越界代替整页效果证据，不复用未覆盖这些内容的历史PASS。

## 列表条数、空值与裁切

这是用户批准的静态展示默认政策，不是iView官方规定。数据列表默认交付10条完整记录，右下角放官方默认Page分页器；用户针对本次页面明确指定数量/分页方式或原型给出明确分页配置时优先遵循。

| 来源情况 | 交付处理 |
| --- | --- |
| 完整记录超过10条 | 只取前10条；其余记录不保存在交付Tree数据或HTML中。初读/复扫仍记录实际可见数量，对不纳入记录注明用户展示政策，不谎称未看见。 |
| 完整记录不足10条 | 保留已有记录，补充演示记录至10条。模型逐条明确完整字段、值、状态和对应操作，保存完整数据；工具不按数量自行扩写。补充遵循已有字段格式和业务关系，不把所有空字段填满。 |
| 整条记录仅露出裁切片段 | 记录片段及裁切事实，不直接创建只有日期等内容的残缺交付行；缺少的展示行按演示补充政策生成，不能把推定值说成已识别原文。 |
| 完整记录中备注等单元格清楚可见但为空 | 保留空值，不因其它行有值而补写；原型明确的“无”或“—”保留其表达。 |
| 单元格被遮挡/裁切而内容未知 | 与空值区别记录。能明确业务结构时可作为演示补充并标注，关键业务含义仍不明则按现有Review处理，不猜称真实内容。 |

在现有观察项/组的`sourceEvidence`及排除`reason`中记录：原图完整条数、裁切片段、保留的来源行号、补充的演示行号及依据、截去范围；不另建报告或输入语言。独立复扫只记实际可见内容，不能把补充记录放进scan假称原图事实。完整Tree保存最终实际10行数据，现有视觉复核分别核对来源行未被改写、补充行被内部标明、空值保留、最终条数与分页位置。来源哈希绑定原图，不作为演示数据真实来源的证明。

分页器用锁定包的官方Page及默认样式，通过布局容器右对齐；默认每页10条，不额外启用尺寸切换、跳转或总数文案。未知总数/页数不编造，不以补足10条推定真实total=10或多页；使用官方默认未提供业务总数的呈现，只把当前第一页作为静态示意。原型明确给出总数时保留。分页存在不意味着实现翻页、hover或接口。

## 新任务的结构化复核门

常规任务采用[快速入口](HTML_FAST_WORKFLOW.md)的紧凑分组输入；逐项编号和以下完整文件由程序展开，AI不重复手写。独立复扫只简记自己从原图看到的组数量、特征、数据差异和例外，仍须实际重看原图，不能从初读自动生成确认。最终复核共同规则只写一次且明确实际检查证据；展开器不会自动判视觉PASS。下面是展开后的证据契约，亦兼容历史输入。

为本次原型保存 `source-observations.json`、`independent-scan.json` 和 `visual-review.json`，三者都绑定原图 `sourceSha256`。前两份分别来自初读和不看初稿的原图复扫；每个可见实例有同一稳定 `id`、`region`，以及 `traits` 中的 `leading`、`trailing`、`surface`、`shape`、`role` 五项呈现类别。初读还记录 `sourceEvidence`、`decision`，纳入项有 `treeRef`，排除项有 `reason`。即使多个菜单共用规则，也要逐项编号。复扫材料只记从图上看到的内容，不复制初读结论。

新任务采用 `reviewMode: "batched-v2"`：顶层 `variantRules` 为每类官方变体只记录一次 `id`、`component`、`variantReason`、`officialEvidence`（锁定版官方源码／文档路径）；每个纳入项只填 `variantRef` 和五项 `renderedTraits`，排除项填 `exclusionStatus`。顶层 `stageChecks` 对 Tree、骨架、组件、交付各给一次结论。初读的顶层 `relations` 每条含稳定 `id`、被覆盖实例的 `sourceIds`、`kind`、`sourceEvidence`；独立复扫的 `relations` 复核相同编号、实例、关系类别并写 `visual` 所见；最终 `relationChecks` 为每个关系记录 `status`、`officialEvidence`、`renderedEvidence`。例如图标与文字的共同间距只写一条关系及其覆盖的实例，例外另列。文件还须锁定三张截图 SHA-256。工具核对来源、实例、关系、综合结论和截图字节；旧任务逐项 `checks` 格式仍可读取，但新任务不用重复填写。

```powershell
rtk proxy .venv/Scripts/python.exe -X utf8 scripts/audit_prototype_observations.py --source artifacts/<任务>/prototype.png --observation artifacts/<任务>/source-observations.json --independent-scan artifacts/<任务>/independent-scan.json --review artifacts/<任务>/visual-review.json --skeleton artifacts/<任务>/skeleton.png --component artifacts/<任务>/component.png --delivery artifacts/<任务>/delivery.png --output artifacts/<任务>/source-visual-qa.json
```

该工具只能证明**已写下的两份观察及组件复核自洽**，不能从像素自动证明没有共同漏项。复扫和最终原图到截图的目视核对仍是独立必做步骤；未运行工具、仍有 Review 或工具 FAIL 时不能宣称完整交付。
## 快速输入补充

新任务使用[快速入口](HTML_FAST_WORKFLOW.md)的`delta-v1`，按实际核对确认来源组和四类结论，只记录差异；程序展开为原有完整审核材料，不再手写重复特征。生成的`review-plan.json`只表达预期，不是视觉PASS。合并审阅图用于集中查看，细节仍看原始截图。局部修正只复用经来源／代码／几何／像素等证明未受影响的已封存组，变化项和全局关系仍核对，不增加串行验收阶段。
